# PDF Takeoff MVP — Spec ("ไม้บรรทัดดิจิทัล" ก่อน AI)

> เกิดจากการวิเคราะห์ตลาด ([01-market-competitors.md](./01-market-competitors.md) + งานวิจัยรอบ 2569-08-24) ที่พบว่า **PDF คือรูปแบบไฟล์ที่ผู้รับเหมาได้รับจริงมากที่สุด** ไม่ใช่ DWG และ pain point ที่ใหญ่ที่สุดไม่ใช่ "นับปริมาณช้า" แต่คือ **"หาสเกลที่เชื่อถือได้ไม่ได้จนต้อง print กระดาษ"** (ประสบการณ์จริงของเจ้าของโปรเจกต์: 2-3 สัปดาห์ต่อโปรเจกต์) — เอกสารนี้คือ spec ของ MVP ตัวแรกที่แก้ปัญหานี้โดยตรง **ไม่มี AI เลยในเวอร์ชันแรก** ใช้หลักการเดียวกับซอฟต์แวร์ถอดแบบมืออาชีพทุกเจ้า (Bluebeam, STACK, PlanSwift, Kreo)

## 1. หลักการ: ตัด "การ print" ออกจาก workflow ไม่ใช่ตัด "คน" ออก

MVP นี้**ไม่แทนที่คนถอดแบบ** — แค่แทนที่ไม้บรรทัด+กระดาษ ด้วยเครื่องมือวัดบนจอที่แม่นกว่าและไม่ต้อง print คนยังเป็นคนตัดสินใจว่าเส้นไหนคือผนัง เส้นไหนคือท่อ เหมือนเดิมทุกอย่าง — สิ่งที่ต่างคือ **สเกลถูกคำนวณจากแบบเอง ไม่ใช่เชื่อขนาดหน้ากระดาษที่ PDF อ้าง**

## 2. User Flow (4 ขั้นตอน)

```
1. Upload PDF → 2. Calibrate Scale → 3. Measure/Takeoff → 4. Export
```

### ขั้นตอน 1 — Upload
- อัปโหลด PDF (รองรับหลายหน้า, เลือกหน้าที่จะทำงานได้)
- แสดง preview ทุกหน้าเป็น thumbnail ให้เลือก

### ขั้นตอน 2 — Calibrate Scale (หัวใจของ MVP นี้)
- แสดงหน้า PDF เต็มจอ
- ผู้ใช้คลิก 2 จุดบน**เส้นบอกขนาดที่มีตัวเลขกำกับอยู่แล้วในแบบ** (เช่น เส้นที่เขียนว่า "5.00") แล้วพิมพ์ค่าจริงเข้าไป (พร้อมหน่วย ม./ซม.)
- ระบบคำนวณอัตราส่วน pixel-ต่อหน่วยจริง แสดงผลให้ยืนยัน
- ⚠️ **ต้องรองรับหลายสเกลในหน้าเดียว** — แบบก่อสร้างมักมีรูปตัด/แบบขยายที่สเกลไม่เท่ากับแปลนหลักในหน้าเดียวกัน (เช่น แปลน 1:100 แต่แบบขยายประตู 1:20) ต้อง calibrate แยกเป็นโซนได้ ไม่ใช่ 1 สเกลต่อ 1 หน้าตายตัว — **นี่คือจุดที่พลาดบ่อยที่สุดถ้าไม่ระวัง**
- เก็บค่า calibration ไว้กับไฟล์ ไม่ต้องทำซ้ำทุกครั้งที่เปิด

### ขั้นตอน 3 — Measure/Takeoff
3 เครื่องมือพื้นฐาน (มาตรฐานเดียวกับซอฟต์แวร์ถอดแบบทุกเจ้า):
| เครื่องมือ | วิธีใช้ | ได้ค่าอะไร |
|---|---|---|
| วัดเส้น (Length) | คลิกจุดต่อจุดตามแนวที่จะวัด | ความยาวรวม (ม.) |
| วัดพื้นที่ (Area) | คลิกปิดรูปหลายเหลี่ยม | พื้นที่ (ตร.ม.) |
| นับจำนวน (Count) | คลิกทีละจุด | จำนวน (นับสะสม) |

- ทุกครั้งที่วัด ผู้ใช้เลือก**หมวดหมู่** จาก dropdown — ใช้ 6 หมวด/หมวดย่อยเดิมจาก [04-category-schema.md](./04-category-schema.md) ได้เลย (งานนี้ format-agnostic ไม่ผูกกับ DWG) เช่น "3.1 งานผนังและฉาบปูน"
- แต่ละรายการที่วัดแสดงเป็น layer ทับบนแบบ (เห็นว่าวัดอะไรไปแล้วบ้าง แก้ไข/ลบทีหลังได้)
- **บันทึกงานระหว่างทำได้ (save/resume)** — งานถอดแบบจริงใช้เวลาหลายชั่วโมงถึงหลายวัน ห้ามบังคับทำรวดเดียวจบ

### ขั้นตอน 4 — Export
- ตารางสรุปปริมาณ จัดกลุ่มตามหมวดที่เลือกไว้ (ยังไม่มีราคาใน v1 — ราคาเป็น Phase 2)
- Export เป็น Excel (แถวเดียวต่อรายการที่วัด + subtotal ต่อหมวด)
- Export PDF ที่มีเส้น/พื้นที่ที่วัดไว้ทับบนแบบเดิม (ใช้ตรวจสอบย้อนหลัง/ส่งให้ลูกค้าดูได้)

## 3. อะไรอยู่ใน MVP อะไรไม่อยู่ (สำคัญ — กันไม่ให้ scope creep)

| อยู่ใน v1 (ขายได้ตอนนี้) | ไม่อยู่ใน v1 (Phase 2+) |
|---|---|
| Calibrate scale ด้วยมือ | Auto-detect สเกลจากข้อความในแบบ |
| วัดเส้น/พื้นที่/นับจำนวนด้วยมือ | Auto-recognize เส้นผนัง/ประตู/หน้าต่างจาก vector data ของ PDF |
| เลือกหมวดหมู่เองจาก dropdown | Auto-categorize |
| Export ปริมาณดิบ (ไม่มีราคา) | ราคาต่อหน่วยอัตโนมัติจาก price list |
| Save/resume โปรเจกต์เดียว | ทำงานพร้อมกันหลายคน (collaboration) |

## 4. แนวทางเทคนิค (ระดับสูง — ยังไม่ implement)

- **หน้าบ้าน:** render PDF ด้วย PDF.js (มาตรฐานตลาด, ฟรี, มี ecosystem รองรับ) วาด canvas/SVG overlay ทับสำหรับคลิกวัด — งานนี้เป็น frontend-heavy ต่างจากงาน DWG parsing เดิมที่เป็น backend/Python ล้วน
- **หลังบ้านที่ต้องมีจริงตั้งแต่ v1:** auth (ผู้ใช้แต่ละคนมีของตัวเอง), เก็บไฟล์/โปรเจกต์ (save/resume), ระบบชำระเงิน (ผูกกับกลไก 100 คนแรกใน [11-founding-member-pricing.md](./11-founding-member-pricing.md)) — **ไม่ต้องมี "core engine ป้องกันการ reverse engineer"** แบบที่ [05-technical-architecture.md](./05-technical-architecture.md) พูดถึงสำหรับงาน DWG เพราะ v1 นี้ไม่มี algorithm ลับอะไรเลย (การคำนวณสเกล/วัดระยะเป็นคณิตศาสตร์พื้นฐานที่รู้กันทั่วไป) — IP จริงของโปรเจกต์นี้อยู่ที่ schema หมวดหมู่/ราคา ไม่ใช่ตัวเครื่องมือวัด
- ยังไม่ตัดสินใจ stack ฝั่ง backend (เหมือนที่ [05-technical-architecture.md §4](./05-technical-architecture.md#4-open-questions-ที่ต้องตัดสินใจก่อนเริ่มเขียนโค้ดจริง) ทิ้งไว้เป็น open question) — เอกสารนี้ focus แค่ product spec ก่อน

## 5. หลักฐานจริง — ทำไม "ใช้หลักการ DXF กับ PDF" ยังทำอัตโนมัติไม่ได้ตอนนี้ (2569-08-25)

> คำถามที่ตรวจสอบ: เอาหลักการ signal-vs-noise/category-schema ที่ใช้กับ DXF (§07) มาทำ 4 ขั้นตอนของ MVP นี้ให้อัตโนมัติ (auto-calibrate, auto-measure) โดยใช้ PDF แทนได้ไหม

**วิธีตรวจ:** เปิดไฟล์ PDF จริงจากลูกค้า (`project/welcome maerem/cad/แบบกาดเวลค่ำกาดฝรั่งแม่ริม.pdf` — ไฟล์เดียวกับที่ถูก "ระเบิด" ออกมาเป็น Kadfarang.dxf ที่ยืนยันแล้วว่าใช้ไม่ได้) ด้วย PyMuPDF ตรวจ 6 หน้าแรกจาก 22 หน้า

**ผลตรวจ:**
| สิ่งที่ตรวจ | ผล |
|---|---|
| Vector drawing objects/หน้า | 7,792–35,355 ชิ้น (ยืนยันเป็น vector จริง ไม่ใช่ภาพสแกน) |
| Raster image ฝังในหน้า | 0 |
| ตัวอักษรที่ extract เป็นข้อความได้ | **0 ทุกหน้าที่ตรวจ (6/6)** |
| Optional Content Groups (= layer name แบบ DWG) | **0** — ไม่มี layer metadata เหลืออยู่เลย |
| ชนิด path segment | เส้นตรง (`l`) 107,468 ชิ้น + quad ทึบ (`qu`) 249 ชิ้น — **ไม่มี bezier curve (`c`) แม้แต่ชิ้นเดียว** |

**สรุปทางเทคนิค:** ไฟล์นี้ถูก export ด้วยเครื่องมือที่ tessellate ทุกอย่าง — รวมถึงตัวอักษร — ให้กลายเป็นเส้นตรงเปล่าๆ ไม่มีป้ายกำกับ (ไม่ใช่แค่ "ตัวหนังสือกลายเป็นเส้นโค้ง" แบบที่ software PDF export ทั่วไปมักทำ — กรณีนี้แย่กว่านั้น คือไม่มี curve object เหลือให้เห็นเค้าโครงตัวอักษรเลยด้วยซ้ำ) นี่คือสาเหตุที่แท้จริงว่าทำไม Kadfarang.dxf ที่แปลงมาจาก PDF นี้ถึงกลายเป็น "เส้นล้วนๆ ไม่มีโครงสร้าง" ตามที่เจ้าของโปรเจกต์ยืนยันไว้ก่อนหน้านี้

**สรุปคำตอบ:**
- เทคนิคทั้งหมดที่สร้างไว้ฝั่ง DXF (Layer Exclusion ตามชื่อ, จับคู่ keyword กับ TEXT/MTEXT, evidentiary threshold ที่อิง Legend/Schedule) **ใช้กับไฟล์ประเภทนี้ไม่ได้เลย** เพราะไม่มีชื่อ layer ให้กรอง ไม่มีข้อความให้อ่าน — เหลือแต่เรขาคณิตล้วนๆ ที่ไม่มีป้ายกำกับ การจะแยก "เส้นนี้คือผนัง" กับ "เส้นนี้คือเส้นบอกขนาด" จากไฟล์แบบนี้ต้องใช้ computer-vision/ML รู้จำผังพื้น (ประมาณ CubiCasa5k-style) ซึ่งเป็นโปรเจกต์วิจัยที่ใหญ่กว่างาน DXF ทั้งหมดที่ทำมาในเซสชันนี้รวมกัน ไม่ควรเอามาผูกกับ MVP
- ⚠️ **ข้อจำกัดของการสรุปนี้:** ตรวจจากไฟล์จริงแค่ 1 ไฟล์ (n=1) จาก pipeline export ที่รู้อยู่แล้วว่าแย่เป็นพิเศษ (เป็นไฟล์ที่ระเบิดเป็น DXF ใช้ไม่ได้มาก่อน) — PDF ที่ export ด้วย driver ที่ดีกว่า (เช่น AutoCAD "Plot to PDF" แบบเปิด "Include Layer Information") มักจะมีทั้งข้อความที่ select ได้จริงและ OCG layer จริง ถ้าเจอไฟล์แบบนั้น auto-detect สเกลจากข้อความตัวเลขบนเส้นบอกขนาดน่าจะพอทำได้บางส่วน — แต่ auto-recognize ผนัง/ประตู/หน้าต่าง (เทียบเท่า classify_layers ของฝั่ง DXF) ยังต้องใช้ computer-vision อยู่ดี เพราะ path ใน PDF ไม่มี entity-type อย่าง LINE/LWPOLYLINE/INSERT ให้อ้างอิงเหมือน DXF
- **ยืนยันการตัดสินใจเดิมใน §3 ของเอกสารนี้:** v1 manual-only (calibrate มือ + วัดมือ) ไม่ใช่แค่ทางเลือกที่ปลอดภัยกว่า แต่เป็น**ทางเดียวที่ทำได้จริงตอนนี้**สำหรับ PDF จำนวนมากในตลาด ส่วน Phase 2 auto-detect ควรระบุเงื่อนไขเพิ่มว่า "ขึ้นกับคุณภาพของ PDF ต้นทาง" ไม่ใช่แค่ "ยังไม่กำหนดเวลา" เฉยๆ

### 5.1 ตัวอย่างที่สาม: PDF ภาพสแกนล้วน (2569-08-25) — เขียนเครื่องมือตรวจสอบให้ "ไพน้อย" แล้ว

หลังจากพยายาม plot ไฟล์ `newhouse 2569.cleaned.v4.dxf` เป็น PDF เพื่อหาตัวอย่าง "PDF คุณภาพดี" มาเทียบ ไฟล์ที่ได้จริง (`project/new house/PDF/แบบก่อสร้างอาคารบ้านพักชั้นเดี่ยว.pdf`) กลับกลายเป็น **ภาพสแกนกระดาษล้วน** (metadata: `producer: Scanner System Image Conversion`) — ไม่ใช่ vector export ที่ตั้งใจจะทดสอบ แต่กลายเป็นตัวอย่างที่สาม ที่มีค่าไม่แพ้กัน

เขียนเครื่องมือตรวจสอบทั่วไป (ไม่ผูกกับไฟล์ใดไฟล์หนึ่ง) ไว้ที่ [`project/code/python/pdf_inspector.py`](./project/code/python/pdf_inspector.py) — จัดประเภทแต่ละหน้าเป็น `vector_with_text` / `vector_no_text` / `raster_scan` / `empty` โดยอัตโนมัติ ตรวจ manual (PyMuPDF ตรงๆ) แล้วรัน `pdf_inspector.py` ซ้ำ **ได้ผลตรงกันทุกตัวเลขตั้งแต่รันแรก** (29/29 หน้า, OCG=0, raster_scan ทุกหน้า, ภาพ 2322×3291px ~212dpi ต่อหน้า)

**ตารางเปรียบเทียบ 3 ตัวอย่างจริงที่เจอมาจนถึงตอนนี้:**

| คุณสมบัติ | สแกนกระดาษ<br>(`แบบก่อสร้าง...pdf`) | Vector ระเบิด<br>(`Kadfarang.pdf`) | DXF ต้นฉบับ<br>(`newhouse.dxf`, ideal) |
|---|---|---|---|
| Vector geometry | ไม่มีเลย (0 ทุกหน้า) | มี (7,792–35,355 ชิ้น/หน้า) | มีเต็ม (LINE/LWPOLYLINE/...) |
| ข้อความอ่านได้ (text object) | ไม่มีเลย | ไม่มีเลย | มีครบ (TEXT/MTEXT) |
| Layer/OCG | ไม่มี | ไม่มี | มี (layer table จริง) |
| ที่มา | สแกนกระดาษจริง | plot/convert จาก CAD แบบ tessellate | ไฟล์ CAD ต้นฉบับ |
| ทางเดียวที่ดึงข้อมูลอัตโนมัติได้ | OCR บนภาพ (เสี่ยงสูงกับข้อความไทยบนแบบก่อสร้าง) | computer-vision รู้จำรูปทรงล้วนๆ (ไม่มีข้อความช่วยเลย) | ใช้เทคนิค signal-vs-noise เดิมได้ตรงๆ |
| Auto-calibrate scale | ทำไม่ได้ | ทำไม่ได้ | ได้บางส่วน (ยังไม่ implement) |
| **เหมาะกับ MVP v1 (manual calibrate+วัดมือ) ไหม** | **ได้ 100%** — คลิกวัดบนภาพที่ render ออกมาเหมือนกับไฟล์ vector ทุกประการ ผู้ใช้ไม่รู้สึกต่างเลย | **ได้ 100%** เหตุผลเดียวกัน | ได้ (แต่ "เปลืองของ" เพราะมี signal ที่เอาไปใช้อัตโนมัติได้แต่ยังไม่ได้ทำ) |

**ข้อสรุปสำคัญที่กลับตรงข้ามกับที่กังวลไว้ตอนแรก:** แม้ไฟล์นี้จะ "แย่ที่สุด" ในแง่ข้อมูลดิบ (ไม่มี vector และไม่มีข้อความเลยแม้แต่นิดเดียว — แย่กว่า Kadfarang ด้วยซ้ำ) แต่**ไม่กระทบ MVP v1 เลยแม้แต่น้อย** เพราะ workflow ที่ออกแบบไว้ (render หน้า PDF ขึ้นจอ → คลิก 2 จุด calibrate → คลิกวัด) ใช้ "ภาพที่มองเห็น" เป็นหลัก ไม่ได้อ่านโครงสร้างข้อมูลเบื้องหลังเลย — ยืนยันว่า **v1 รองรับ PDF ภาพสแกนได้ตั้งแต่ต้นโดยไม่ต้องแก้อะไรเพิ่ม** (ปิด open item ใน [BACKLOG.md](./BACKLOG.md) ได้บางส่วน เหลือแค่คำถามเรื่อง DPI ขั้นต่ำที่ยอมรับได้สำหรับความแม่นยำตอน calibrate — ไฟล์ตัวอย่างอยู่ที่ ~212dpi ซึ่งน่าจะพออ่านตัวเลขเส้นบอกขนาดด้วยตาได้ แต่ยังไม่ได้ทดสอบจริงว่าซูมเข้าไปมากๆ แล้วเบลอจนอ่านไม่ออกหรือเปล่า)

**ยังค้างอยู่:** ยังไม่เคยได้ตัวอย่าง PDF ที่ plot จาก CAD แบบมี vector+ข้อความจริง (คอลัมน์ขวาสุดในตารางยังเป็น "ideal" ทางทฤษฎี ไม่ใช่ไฟล์จริงที่ตรวจแล้ว) — ถ้าจะ plot ให้ลองอีกครั้งต้องเช็คตั้งค่า driver ให้เป็น "PDF" ไม่ใช่ path ที่ไปเข้าเครื่องสแกนจริง

### 5.2 ตัดสินใจทิศทาง (2569-08-25): สแกนกระดาษมีตราประทับเทศบาล = เคสหลัก ไม่ใช่เคสสำรอง

เจ้าของโปรเจกต์ชี้ทิศทางใหม่: แนวทางที่จะเดินคือยึด**แบบที่ได้รับใบอนุญาตก่อสร้างจริงจากเทศบาล มีตราประทับ+ลายเซ็นรับรอง**เป็นต้นแบบหลัก แม้จะเป็น PDF ภาพสแกน (ไม่ใช่ vector) เพราะนี่คือสิ่งที่ผู้รับเหมา/เจ้าของบ้านมีอยู่แล้วจริงๆ ในสัดส่วนส่วนใหญ่ (~90% ตามประสบการณ์เจ้าของโปรเจกต์) — ต่างจาก "PDF vector สวยๆ ที่ export จาก CAD" ซึ่งเป็นกรณีที่หวังจะได้ ไม่ใช่กรณีที่มักได้จริง

**ยืนยันด้วยภาพจริง:** render หน้า 1 ของ `แบบก่อสร้างอาคารบ้านพักอาศัยชั้นเดียว...pdf` ออกมาดู พบตราประทับ **"เทศบาลตำบลสันปูเลย"**, กล่องใบอนุญาตเลขที่ 503-2568, ลายเซ็นจริงครบ 5 ตำแหน่ง (ตรวจหลักฐาน/ตรวจสถานที่/ผู้อำนวยการกองช่าง/ปลัดเทศบาลตำบล/นายกเทศมนตรีตำบล) และที่อยู่ตรงกับโปรเจกต์ newhouse (ต.สันปูเลย อ.ดอยสะเก็ด จ.เชียงใหม่) — **ยืนยันไฟล์นี้คือแบบก่อสร้างที่ได้รับอนุญาตจริงตามที่ต้องการพอดี**

**ผลที่ตามมา:**
- **ตั้งไฟล์นี้เป็นต้นแบบ (prototype reference) อย่างเป็นทางการ** สำหรับพัฒนา/ทดสอบ MVP v1 ต่อจากนี้ — ไม่ใช่แค่ตัวอย่างทดสอบเฉยๆ
- มี ground truth คู่กันพร้อมใช้ทันที: `BOQ - new house.xls` (โปรเจกต์เดียวกัน) — เทียบผลวัดจาก PDF กับ BOQ จริงได้เลยไม่ต้องหาไฟล์ใหม่
- กลับลำดับความสำคัญของ item ใน §7 (เดิมเขียนว่า "เริ่มจาก vector PDF ก่อนเพื่อความง่าย") — **สแกนกระดาษมีตราประทับคือเคสหลักที่ต้องออกแบบ/ทดสอบรอบแรก** ไม่ใช่ vector PDF
- ⚠️ ไฟล์นี้มีข้อมูลส่วนบุคคลจริง (ชื่อ-ที่อยู่เจ้าของบ้าน, เลขที่ใบอนุญาต) — ใช้ได้ภายในงานพัฒนานี้ตามปกติ แต่ระวังเวลาจะเผยแพร่/แชร์ตัวอย่างออกไปนอกทีม

### 5.3 ทดสอบนับรายการจริง 1 ตัวอย่าง (2569-08-26): D1 ประตูบานเลื่อน — วัดมือได้แม่น ระบบอัตโนมัติได้ 3/4

> ทดสอบ: หมวด 1 รายการ 1 ใน BOQ ("รางวัดขอบเขตที่ดิน") เป็นงานเหมา ไม่มีปริมาณเชิงเรขาคณิตให้วัด (ดูใน BACKLOG) — เปลี่ยนไปทดสอบรายการที่นับง่ายที่สุดแทน: **Arch sheet 4.1 "D1 ประตูบานเลื่อนอลูมิเนียม+บานติดตาย -- 4.0 ชุด"**

**ขั้นตอนที่ 1 — วัดมือ (จำลอง MVP v1):** เปิดหน้า A-04 (แปลนพื้น, หน้า 5 ของ PDF) เทียบกับหน้า A-10 (แบบขยายประตู, หน้า 11 — ยืนยันว่า D1 คือประตูบานเลื่อนอลูมิเนียม 4 บาน กว้าง 4.60ม.) นับป้าย "D1" บนแปลนพื้นด้วยตาทีละจุด **พบ 4 จุด** — ตรงกับ BOQ (4.0 ชุด) เป๊ะ

**ขั้นตอนที่ 2 — เขียน "ไพน้อย" ให้รันอัตโนมัติ:** ไฟล์นี้เป็นภาพสแกนล้วน (§5.1) ไม่มี text/vector ให้ grep และไม่มี OCR/OpenCV/scipy ติดตั้งในเครื่อง (เช็คแล้ว) — เขียน [`pdf_door_label_matcher.py`](./project/code/python/pdf_door_label_matcher.py) ใช้ **normalized cross-correlation ผ่าน FFT ล้วนๆ (numpy เท่านั้น)** จับคู่ template ป้าย "D1" ที่ครอปมาจากจุดที่ 1 กับทั้งหน้า

**ผลรอบแรก:** เจอ 3 จุดด้วย score เกือบสมบูรณ์ (0.97–1.00, ตรงกับ 3 ใน 4 จุดที่วัดมือเป๊ะ) แต่จุดที่ 4 (ป้ายที่อยู่ติดสัญลักษณ์ลูกศร+เส้นผนังแนวตั้ง) ได้ score แค่ ~0.52–0.59 **ปนอยู่กับ false positive อื่นๆ อีกกว่า 100 จุดที่ score ใกล้เคียงกัน** ไม่มี threshold ไหนที่ตัดแยกจุดที่ 4 ออกจากสัญญาณรบกวนได้สะอาด

**ขั้นตอนที่ 3 — พยายามแก้:** (1) ครอป template ให้แน่นขึ้น (ตัด whitespace ส่วนเกิน) — ไม่ช่วย ช่องว่างคะแนนยังเท่าเดิม (2) ลองใช้จุดที่ 4 เองเป็น template แทน — พบว่า template จากจุดนั้น "เสีย" ไปแล้วตั้งแต่ต้น (ให้ 443 matches ทั่วหน้า) เพราะลูกศร+เส้นผนังที่ทับซ้อนกับตัวอักษรทำให้ pixel pattern ปนเปื้อน ไม่ใช่ "D1" บริสุทธิ์อีกต่อไป — **สรุปว่านี่คือข้อจำกัดเชิงโครงสร้างของวิธีนี้ ไม่ใช่แค่ต้องจูน threshold เพิ่ม**

**ตารางเปรียบเทียบ:**

| | วัดมือ (จำลอง MVP v1) | ไพน้อย (template matching, ไม่มี OCR) |
|---|---|---|
| จำนวน D1 ที่พบ | 4/4 | 3/4 (จุดที่ 4 แยกจาก noise ไม่ได้) |
| ตรงกับ BOQ (4.0 ชุด) ไหม | ตรง 100% | ไม่ตรง ขาด 1 จุด |
| ต้องอาศัยอะไร | คนอ่านป้าย+เทียบตารางประตู (A-10) ด้วยตา | ต้องมี template สะอาดที่ไม่ถูกกราฟิกอื่นทับ |
| จุดอ่อนที่เจอ | ไม่มี (งานที่คนถนัดอยู่แล้ว) | ล้มเหลวเมื่อสัญลักษณ์อื่น (ลูกศร/เส้นผนัง) ทับซ้อนกับข้อความ — เกิดขึ้นได้ทุกเมื่อในแบบจริง |
| generalize ข้ามหน้า/โปรเจกต์อื่นไหม | ได้ (คนอ่านภาษาไทย/สัญลักษณ์ CAD เป็น) | ไม่ได้เลย — ผูกกับ font/ตำแหน่งเป๊ะของไฟล์นี้ไฟล์เดียว |

**สรุป:** ยืนยันสิ่งที่ [10-pdf-mvp-spec.md §5](#5-หลักฐานจริง--ทำไมใช้หลักการ-dxf-กับ-pdf-ยังทำอัตโนมัติไม่ได้ตอนนี้-2569-08-25) เขียนไว้แล้วว่า Auto-recognize ต้องใช้ computer-vision/ML จริง ไม่ใช่ template matching ธรรมดา — เคสนี้เป็นหลักฐานเชิงประจักษ์ชิ้นแรกที่แสดงให้เห็นตัวเลขจริง (75% recall, แยก false positive ไม่ได้) ไม่ใช่แค่การคาดเดา ยืนยันอีกครั้งว่า **v1 ต้องเป็นวัดมือ ไม่ใช่ auto-count** และ Phase 2 auto-recognize ถ้าจะทำจริงต้องลงทุน OCR/ML ไม่ใช่แค่ template matching แบบนี้

### 5.4 ขยายทดสอบ: D4/D5 — คนสองคนนับตรงกัน, ไพน้อยแยก false positive ไม่ได้เลย (2569-08-26)

เจ้าของโปรเจกต์นับ D4/D5 จากแบบ A-04 เองด้วยตา (วงกลม/สี่เหลี่ยมทุกจุด) ได้ **D4 = 5 บาน, D5 = 4 บาน** — ผู้เขียน (Claude) นับอิสระแยกต่างหากโดยไม่ดูผลของเจ้าของโปรเจกต์ก่อน (ไล่ทีละ crop ของภาพเดียวกัน) ได้ผล **เท่ากันเป๊ะทั้งสองจำนวน** — เป็นการยืนยันไขว้ (cross-validate) ว่าการนับด้วยมือน่าเชื่อถือ ไม่ใช่ตัวเลขบังเอิญ

รัน `pdf_door_label_matcher.py` ต่อกับ template "D4" และ "D5" (ครอปจากจุดที่ชัดเจนที่สุดของแต่ละรหัส):

| | คาดหวัง (นับมือ 2 คนตรงกัน) | ไพน้อย (template matching) |
|---|---|---|
| D1 | 4 | 3 จุดชัด (score 0.97–1.00) + 1 จุดปนกับ noise — **แยกได้บางส่วน** |
| D4 | 5 | **แยกไม่ได้เลย** — 12 จุดคะแนนเกาะกลุ่มกันแน่น (0.71–0.73) ไม่มี threshold ไหนตัดสัญญาณจริงออกจาก false positive ได้ |
| D5 | 4 | **แยกไม่ได้เลย** — 8 จุดคะแนนเกาะกลุ่มกัน (0.71–0.78) ก่อนจะร่วงลง เกินจำนวนจริงไปเกือบเท่าตัว |

**ทำไม D4/D5 แย่กว่า D1:** ป้าย D1 บนแบบนี้บังเอิญมีบริบทรอบข้าง (ช่องว่าง, ตำแหน่งบนผนัง) ที่ไม่ซ้ำใครมากพอจะแยกได้ แต่ป้าย D4/D5 มีรูปแบบ 2 ตัวอักษร+กล่องเดียวกับ D2/D3/W3/W4 ฯลฯ ที่กระจายอยู่ทั่วแบบ — normalized cross-correlation แยกความต่างระหว่าง "D4" กับ "D5"/"W4"/"D2" ไม่ได้ดีพอ เพราะโครงสร้าง pixel โดยรวม (กรอบ, ขนาดตัวอักษร, ความหนาเส้น) คล้ายกันมาก ต่างกันแค่ตัวเลข/ตัวอักษร 1 ตัวซึ่งเป็นสัดส่วนพื้นที่เล็กเกินไปที่จะมีน้ำหนักในคะแนนรวม

**สรุปที่แน่นขึ้นกว่าเดิม:** ผลลัพธ์ไม่คงเส้นคงวาข้ามรหัส (D1 พอใช้ได้บางส่วน, D4/D5 ใช้ไม่ได้เลย) — แปลว่า **ไม่มีทางตั้ง threshold ตายตัวที่ใช้ได้ทั่วทั้งไฟล์** ต้องปรับ per-label ด้วยมือทุกครั้ง ซึ่งเท่ากับไม่มีประโยชน์ในทางปฏิบัติ ยิ่งตอกย้ำว่า **v1 ต้องเป็นคนวัดมือ 100%** และการันตีว่าคนสองคนอ่านแบบเดียวกันแล้วได้ตัวเลขตรงกัน (ตามที่พิสูจน์แล้วในการทดลองนี้) น่าเชื่อถือกว่าอัลกอริทึมง่ายๆ มาก

## 6. เกณฑ์ที่แปลว่า MVP นี้ "พอขายได้"

- ผู้ใช้ทำ calibrate + วัดปริมาณทั้งหน้าได้จริงโดยไม่ต้อง print กระดาษเลยสักครั้ง
- เวลาที่ใช้ต่อโปรเจกต์ **น้อยกว่า** วิธีเดิม (2-3 สัปดาห์) อย่างมีนัยสำคัญ — ยังไม่ตั้งตัวเลขเป้าที่ชัดเจน (ดู [BACKLOG.md](./BACKLOG.md))
- Export ออกมาใช้งานต่อได้จริงในรูปแบบที่ผู้รับเหมาคุ้นเคย (Excel)
