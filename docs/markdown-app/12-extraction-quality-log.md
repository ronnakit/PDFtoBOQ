# บันทึกคุณภาพการถอดข้อมูล (Extraction Quality Log)

บันทึกทุกครั้งที่ไพน้อย/Claude อ่านข้อมูลจากแบบด้วย Vision API จริง (ไม่ใช่แค่ Claude อ่านในแชทเฉยๆ) — เพื่อสะสมเป็นข้อมูลวิเคราะห์ pattern ของปัญหาที่เกิดซ้ำ ใช้ประกอบการตัดสินใจตอนถอดแบบโปรเจกต์อื่นในอนาคต ไม่ใช่แค่บันทึกไว้เฉยๆ

**วิธีใช้:** ทุกครั้งที่รันการถอดข้อมูลจริง (ไม่ว่า Stage ไหน) เพิ่มแถวใหม่ในตารางที่เกี่ยวข้องด้านล่าง — ระบุปัญหาที่เจอจริงหลังตรวจสอบ (ไม่ใช่แค่ "รันผ่าน") และจัดหมวดปัญหาตามรายการหมวดที่กำหนดไว้ท้ายไฟล์ ถ้าไม่พบปัญหาให้เขียน "ไม่พบ" ไม่ใช่เว้นว่าง

**ข้อสังเกต:** งาน "นับรหัสบนกริดที่มีป้ายกำกับชัดเจน" (เหมือน S-01) จัดอยู่ในกลุ่มเดียวกับประตู/หน้าต่าง/ตาราง schedule ที่แม่นยำสูง — ยืนยันเพิ่มเติมว่าปัญหาที่แท้จริงของงานประเภทนี้คือ **max_tokens ไม่พอสำหรับ adaptive thinking ของ Sonnet 5** ไม่ใช่ความสามารถในการอ่าน — ต้องตั้ง max_tokens สูงพอเสมอ (10000+) สำหรับงานที่ต้อง "ไล่นับ/สแกน" ทั้งหน้า ไม่ใช่แค่ตอบสั้นๆ

## หมวดปัญหา (ใช้ให้ตรงกันทุกแถว)

- **code-bug** — ปัญหาที่ตัวโค้ด ไม่ใช่ตัว AI (เช่น เช็คขนาดผิด, ครอปผิดตำแหน่ง, max_tokens ไม่พอ) — แก้แล้วไม่กลับมาเป็นอีก
- **hallucination (dense-table text)** — โมเดลอ่านตาราง/ข้อความหนาแน่นผิดทั้งที่ภาพชัด ไม่ใช่ปัญหาความละเอียด
- **resolution-hallucination** — ผิดเพราะ DPI ต่ำเกินจริง (แก้ด้วยการเพิ่ม DPI ได้จริง)
- **shape-misread** — อ่านรูปทรง/ตัวอักษรในสัญลักษณ์ผิด (เช่น ป→ปฏ, หกเหลี่ยม→ข้าวหลามตัด)
- **hatch-pattern-misread** — อธิบายลาย hatch วัสดุผิดจากภาพจริง
- **field-swap** — เนื้อหาถูกแต่ใส่สลับช่อง/ป้ายกำกับผิดคู่ (พบซ้ำหลายรอบ คนละคู่ทุกครั้ง — ดูเหมือนเป็น pattern ของโมเดลเอง ไม่ใช่ fluke ครั้งเดียว)
- **date-misread** — วันที่ตราประทับ/เลขที่เอกสารอ่านไม่ตรงกันระหว่างรอบ (มักเป็นตราที่เลอะ/ซ้อนทับจริง ไม่ใช่ resolution)
- **bbox-position-miss** — โมเดลบอกได้ถูกว่าสัญลักษณ์คืออะไร แต่บอกพิกัดกรอบ (pixel/% ของหน้า) ไม่แม่น บางจุดพลาดไปคนละแถว/คนละตำแหน่งเลย ไม่ใช่แค่คลาดเคลื่อนเล็กน้อย — เป็นข้อจำกัดที่รู้จักกันทั่วไปของ vision-LLM (เก่งเรื่องอ่าน/จำแนก แต่ไม่เก่งเรื่องบอกพิกัดที่แม่นยำ)
- **verification-gap** — ผู้ตรวจ (ในที่นี้คือ Claude เอง) ตรวจสอบด้วยวิธีที่ไม่เพียงพอ (เช่น ดูภาพรวมย่อส่วนแทนที่จะเปิดไฟล์ผลลัพธ์จริงทีละไฟล์) ทำให้ error หลุดผ่านการตรวจไปได้ — คนละสาเหตุจาก AI อ่านผิด แต่ผลลัพธ์ปลายทางเหมือนกัน (ข้อมูลผิดหลุดออกไป)
- **human-review-reversal** — คนตรวจสอบแก้ไขบางอย่างแล้วภายหลังพบว่าที่แก้ไปผิด กลับคำแก้ไขเอง — ไม่ใช่ error ของ AI/โค้ด แต่บันทึกไว้เพื่อความโปร่งใสของกระบวนการทั้งหมด

## ข้อสังเกตจาก 11 รอบแรก (Stage 0)

- **งาน "อ่านโค้ด/ตัวเลขเดี่ยวๆที่มีป้ายกำกับ" (title block DWG NO.) แม่น 100% ทุกรอบ** — ไม่เคยเจอปัญหาเลยตลอด 11 รอบ ยืนยันอีกครั้งว่าเป็นจุดแข็งของ AI
- **field-swap เกิดซ้ำทุกรอบที่มีตาราง/legend หลายรายการติดกัน แต่คนละคู่ทุกครั้ง** (รอบ 8: รูปตัด/รูปด้าน, รอบ 9: เหล็ก/ดิน) — นี่คือเหตุผลที่ทำให้ตัดสินใจสร้างรูปครอปสัญลักษณ์ฝังในไฟล์ (ดู `project/new house/symbols/`) แทนที่จะพึ่งคำบรรยายเป็นข้อความอย่างเดียว
- **date-misread บนตราประทับ/สแตมป์ที่มีลายเซ็นทับซ้อน** เป็นปัญหาจริงที่อาจแก้ด้วย prompt ไม่ได้ง่ายๆ — ตัดสินใจแล้วว่าไม่ใช่สาระสำคัญ ให้คนแก้เอง ไม่ลงทุนแก้อัตโนมัติ
- **bbox-position-miss (รอบ 10) เป็นข้อจำกัดคนละแบบจาก field-swap** — โมเดล "รู้" ว่าสัญลักษณ์คืออะไรถูกต้อง (พิสูจน์จากคำอธิบายที่ถูกในรอบก่อนๆ) แต่ "บอกพิกัด" ผิด — สรุปว่า vision-LLM ปัจจุบันยังไม่เหมาะกับงานบอกตำแหน่ง pixel-precise ล้วนๆ ต้องมีคนตรวจ/แก้ตัวเลขเสมอ (ออกแบบ `--recrop-only` ให้แก้ตัวเลขแล้วครอปใหม่ได้โดยไม่ต้องเรียก API ซ้ำ)
- **verification-gap (รอบ 11) คือบทเรียนสำคัญที่สุดของรอบนี้: "ตรวจสอบด้วยตา" ต้องหมายถึงเปิดไฟล์ผลลัพธ์สุดท้ายจริงๆ ทีละไฟล์ ไม่ใช่ดูภาพรวม/ภาพย่อส่วนแล้วสรุปว่าโอเค** — กฎเดียวกับที่ใช้ตรวจ AI ต้องใช้กับตัวเองด้วยเวลาคำนวณพิกัด/ครอปภาพเอง ไม่มีข้อยกเว้น
