# สัญญาณ vs ขยะ: กรอบคิดสำหรับแยกสิ่งที่ "เกี่ยวกับ BOQ" ออกจากสิ่งที่ "วาดไว้ช่วยเขียนแบบเฉยๆ"

> เกิดจากการวิเคราะห์หลังรัน [pynoi_parser.py](./project/code/python/pynoi_parser.py) กับ `newhouse 2569.dxf` จริง (ดู [LOG.md](./LOG.md)) — สมมติฐานตั้งต้นของเอกสารนี้คือ **"ไพน้อย" ไม่รู้จักแบบนี้มาก่อนเลย เหมือนนักถอดแบบที่เพิ่งได้รับไฟล์มาเป็นครั้งแรก และแบบไม่มีทางสมบูรณ์แบบ 100%** — ต้องมีขั้นตอนพิสูจน์ทุกเลเยอร์/ทุกก้อนเรขาคณิตก่อนนับเป็นปริมาณ ไม่ใช่เชื่อว่าทุกเส้นในไฟล์คือของจริงที่ต้องคิดราคา
>
> ⚠️ **หลักคิดตั้งต้นที่ต้องยึดตลอดทั้งโปรเจกต์ (เพิ่มเข้ามาหลังทบทวนเพิ่มเติม):** อย่าหลงคิดว่าแบบ CAD ที่ลูกค้าส่งมาจะสะอาดเหมือนตำราเรียน ในโลกความเป็นจริง **แบบ CAD ส่วนใหญ่คือสนามอารมณ์และกองขยะดิจิทัล** — ดราฟต์แมน/สถาปนิกเวลาเร่งรีบทิ้งร่องรอยความรีบร้อนไว้เต็มไปหมด ถ้าระบบมองไม่ขาด มันจะเอาขยะเหล่านี้ไปคำนวณจน BOQ พังยับเยินทันทีโดยที่ตัวเลขยัง "ดูสมเหตุสมผล" (ไม่ error ให้เห็น)

## 1. ทำไมเรื่องนี้ถึงเป็นหัวใจของทั้งโปรเจกต์

ถ้าแยกไม่ออก ผลลัพธ์ BOQ จะผิดแบบที่ "ดูสมเหตุสมผล" (ตัวเลขออกมาไม่ error แต่ผิดมหาศาล) เหมือนกรณีจริงที่เจอแล้ว: เลเยอร์ `WALL` มีพื้นที่รูปปิดรวมกัน 289,034 ตร.ม. — สำหรับบ้านหลังเดียวขนาด < 300 ตร.ม. ตัวเลขนี้ผิดกว่า 1,000 เท่า เพราะเลเยอร์เดียวกันมีทั้งขอบผนังจริง เส้นกรอบ hatch ปลีกย่อย เส้นช่วยร่างที่ไม่มีใครลบ ปนกันหมด **นี่คือความเสี่ยงเดียวที่ทำให้ AI Auto-BOQ ทั้งระบบใช้งานไม่ได้จริงถ้าไม่แก้**

## 2. คำถาม 5 ข้อที่ต้องตอบให้ได้ก่อนนับปริมาณอะไรก็ตาม

ก่อนจะ sum ความยาว/พื้นที่จากเส้นไหนก็ตาม ต้องตอบให้ได้ก่อนว่า:

1. **อยู่ใน Model Space หรือ Paper Space/Layout?** — Layout คือหน้ากระดาษพิมพ์ (title block, กรอบ A3, scale bar) ไม่ใช่เรขาคณิตจริง 1:1 ห้ามนำมานับปริมาณเด็ดขาด
2. **เป็นเรขาคณิตของสิ่งก่อสร้างจริง หรือเป็น annotation/เครื่องมือช่วยอ่านแบบ?** — เส้นบอกขนาด (dimension), leader, north arrow, grid reference line ไม่ใช่ตัวอาคาร
3. **เป็นงานใหม่ งานเดิมที่ต้องรื้อ หรืองานเดิมที่คงไว้?** — สำคัญมากสำหรับงานรีโนเวท (สีเส้น/เลเยอร์มักเข้ารหัสไว้ แต่ไม่มีมาตรฐานสากลตายตัว ต้องเทียบกับ Legend ในแบบเสมอ)
4. **เป็น block ตกแต่ง/แสดงบรรยากาศ หรือ block แทนวัสดุก่อสร้างจริง?** — ต้นไม้ รถ คน เฟอร์นิเจอร์ลอยตัว ไม่ใช่วัสดุที่ต้องตีราคา
5. **ถ้ามีตาราง Legend/Schedule ที่คนเขียนระบุจำนวนไว้แล้ว ตัวเลขจากรูปทรงเรขาคณิตตรงกับตารางนั้นไหม?** — ถ้าไม่ตรง ต้อง flag ความขัดแย้งไว้ ไม่ใช่เลือกเชื่อฝั่งใดฝั่งหนึ่งเอง

## 3. หลักฐานจริงจาก `newhouse 2569.dxf` — สิ่งที่เจอแล้วในไฟล์นี้ไฟล์เดียว

| ประเภทขยะ | ตัวอย่างที่เจอจริงในไฟล์ | ทำไมถึงเป็นขยะสำหรับ BOQ |
|---|---|---|
| กรอบกระดาษ/Title block | เลเยอร์ `Bodr A3` (area รวม 39,299 — คือกรอบ A3 ที่สเกลผิดมาตราส่วน ไม่ใช่พื้นที่จริง), `TITLE`, `LOGO`, `FRAME` | เป็น layout อุปกรณ์การพิมพ์ ไม่ใช่ตัวอาคาร |
| Auto-generated เฉพาะของ AutoCAD | เลเยอร์ `DEFPOINTS` (area รวม 113,955 — AutoCAD สร้างอัตโนมัติสำหรับเก็บจุดอ้างอิงของ dimension, **ตั้งค่าให้ไม่ถูกพิมพ์ (non-plotting) โดยดีฟอลต์เสมอ**) | ไม่มีความหมายทางกายภาพเลย เป็นแค่จุดคำนวณภายในของ dimension |
| เส้นบอกระยะ/annotation | เลเยอร์ `DIM`, `DIMENSION`, `S-DIM`, entity ประเภท `DIMENSION`/`LEADER` ทั่วทั้งไฟล์ | คือตัวเลข/เส้นชี้บอกระยะ ไม่ใช่ผนังหรือวัสดุ |
| เส้นกริดโครงสร้าง | เลเยอร์ `GRID` (length รวม 2,375) | เป็นเส้นอ้างอิงตำแหน่งเสา/แนวโครงสร้าง ไม่ใช่วัสดุที่ต้องตีราคาเอง |
| Block ตกแต่ง/แสดงบรรยากาศ | block ชื่อ `Human_01`, `corolla`, `BMW 820 oben`, `Shrub 4`, `TREE_P01`, `TREE_P31`, `TREE_P34`, `TREE_P36`, `TREE_P38`, `Tree-2`, `Tree-25`, `Tree-3`, `CAR_P_10` | คนวางไว้เพื่อ "ให้ภาพดูมีชีวิตชีวา" เวลาพรีเซนต์ลูกค้า ไม่ใช่รายการที่ต้องซื้อ/ก่อสร้าง |
| เลเยอร์ default/ไม่ได้ตั้งชื่อ | เลเยอร์ `0` (มี entity 12 ประเภทปนกันหมด ตั้งแต่ ARC ถึง TEXT) | เป็นเลเยอร์ที่คนลืมย้ายวัตถุออกไปเลเยอร์ที่ถูกต้อง เชื่อถือไม่ได้เลยว่าอะไรอยู่ในนั้น |
| ตาราง/ข้อความที่ไม่ใช่เรขาคณิต | เลเยอร์ `TABLE`, `TEXT`, `SPEC` | มีค่าเป็น **ข้อมูล** (ตัวเลขในตาราง Legend) ไม่ใช่รูปทรงที่วัดพื้นที่ได้ — ต้องอ่านเป็น text ไม่ใช่ sum เป็น area |

⚠️ ทั้งหมดนี้คือสิ่งที่ **เจอแล้วจริงในไฟล์เดียว** ยังไม่ได้ตรวจสอบไฟล์ที่สอง (Kadfarang/welcome maerem) — คาดว่าจะเจอ pattern คล้ายกันแต่ตั้งชื่อเลเยอร์ต่างออกไปอีกชุด (คนละคนวาด คนละมาตรฐาน) นี่คือเหตุผลที่ต้องมี §4 ด้านล่าง — taxonomy ที่ไม่ผูกกับไฟล์ใดไฟล์หนึ่ง แต่เป็นพฤติกรรมการเขียนแบบที่เกิดซ้ำในทุกไฟล์

## 4. 🗑️ 4 ประเภท "ขยะในการเขียนแบบ" ที่เกิดซ้ำได้ทุกไฟล์ (Drafting Garbage by Behavior)

ต่างจาก §3 ที่เป็นหลักฐานเฉพาะไฟล์นี้ไฟล์เดียว ส่วนนี้คือ taxonomy เชิงพฤติกรรมของดราฟต์แมน/สถาปนิกที่เกิดซ้ำได้ในทุกไฟล์ ไม่ว่าใครจะเป็นคนวาด — ต้องล่าและกำจัดในขั้นตอนเตรียมการเสมอ

### 4.1 เส้นช่วยวาดและเส้นเล็งแนว (Construction & Helper Lines)
- **ลักษณะ:** เส้นประ เส้นยาว หรือเส้นเอียงที่ดราฟต์แมนลากขึ้นมาเพื่อ "เล็งแนว" จัดตำแหน่งเสาหรือหน้าต่างให้ตรงกันตอนเขียนแบบ
- **ผลกระทบถ้าไม่กรอง:** ระบบจะเข้าใจว่าเป็นผนังหรือแนวคานจริง แล้วเอาความยาวไปบวกเข้า BOQ ทำให้ปริมาณปูนฉาบหรือโครงสร้างเพี้ยน

### 4.2 ลวดลายวัสดุและลายตัด (Hatch Patterns & Details)
- **ลักษณะ:** เส้นยิบย่อยนับพันเส้นที่ถูกสร้างขึ้นเพื่อแสดงสัญลักษณ์คอนกรีต (`AR-CONC`), ลายอิฐฉาบ, หรือลายดินตัดในรูปตัด (Section)
- **ผลกระทบถ้าไม่กรอง:** ถ้าระบบสแกนเจอเส้นเหล่านี้แล้วนับเป็น entity วัตถุงานโครงสร้าง ตัวเลขปริมาณเหล็กหรือคอนกรีตจะพุ่งทะยานจนน่าตกใจ (กลายเป็นขยะคำนวณขนาดใหญ่)

### 4.3 กรอบกระดาษ วิวพอร์ต และข้อความหมายเหตุรอบนอก (Viewports, Title Blocks & Off-site Notes)
- **ลักษณะ:** กรอบกระดาษ A1/A3, ตารางประวัติการแก้แบบ (Revision Table), โลโก้บริษัท หรือข้อความโน้ตจิปาถะที่กองอยู่รอบนอกแปลนหลักใน Model Space
- **ผลกระทบถ้าไม่กรอง:** ระบบจะดึงข้อความเหล่านี้เข้ามาปะปนกับสเปกวัสดุจริง ทำให้พจนานุกรมข้อมูล (Dictionary) รวนและจับคู่หมวดหมู่ผิดเพี้ยน

### 4.4 เส้นซ้อนทับและซากแบบเก่า (Overkill & Orphaned Entities)
- **ลักษณะ:** เส้นที่ถูกลากทับซ้อนกัน 2-3 รอบตอนแก้แบบ (เช่น ผนังเก่าถูกย้ายแต่ลืมลบเส้นเดิมทิ้ง แค่ลากเส้นใหม่ทับ) หรือบล็อกอุปกรณ์ที่ระเบิด (explode) ทิ้งไว้จนกลายเป็นเส้นกระจัดกระจาย
- **ผลกระทบถ้าไม่กรอง:** ความยาว/จำนวนถูกนับซ้ำ 2-3 เท่าโดยไม่มีทางรู้ได้จากการ sum ตรงๆ

## 5. 🛠️ กลไกที่ต้องสร้าง: ระบบคัดกรองขยะ CAD (CAD Noise Filtering Engine)

ต้องมีอีก 1 ชั้นในขั้นตอนเตรียมการ **ก่อน** เข้าสู่การประมวลผล/คำนวณปริมาณ ประกอบด้วย 3 กลไก:

1. **Bounding Box Filter** — ตัดกรอบพื้นที่นอกเหนือจากขอบเขตอาคารหลักทิ้งทั้งหมด (ตัดกรอบกระดาษ/ข้อความรอบนอกที่กองอยู่นอกตัวอาคาร) แนวทางทำจริง: หาก cluster เชิงพื้นที่ของ entity ทั้งหมด (เช่น ด้วย bounding-box overlap หรือ spatial clustering) แล้วถือว่า cluster ที่ใหญ่ที่สุด/หนาแน่นที่สุดคือ "ตัวอาคาร" ส่วนที่อยู่นอกกรอบนั้นไกลๆ (title block, notes ขอบกระดาษ) คือผู้ต้องสงสัยอันดับแรก
2. **Layer Exclusion** — เพิกเฉยต่อเลเยอร์ที่เป็นเส้นช่วยวาดโดยอัตโนมัติ ด้วย denylist คำสำคัญ (ไม่สนตัวพิมพ์เล็ก-ใหญ่ ตรวจแบบ substring): `HATCH`, `CONSTRUCT`, `HELP`, `VIEWPORT`, `DIM`, `GRID`, `TITLE`, `BORDER`/`Bodr`, `DEFPOINTS`, `NOTE` — ⚠️ เป็นแค่ตัวกรองรอบแรก ไม่ใช่ตัวตัดสินสุดท้าย เพราะชื่อเลเยอร์เชื่อถือไม่ได้ 100% (ดู §6 ข้อ 5) ต้องใช้ร่วมกับ heuristic อื่น
3. **Duplicate Purge** — กำจัดเส้นที่ทับซ้อนกันสนิท (คล้ายคำสั่ง `OVERKILL` ของ AutoCAD) ออกจากฐานข้อมูลดิบก่อนนำความยาวมาคำนวณ แนวทางทำจริงด้วย ezdxf: จัดกลุ่ม entity ตาม (ประเภท, เลเยอร์) แล้วเทียบพิกัดจุดเริ่ม/จุดจบ (หรือ vertex list ของ LWPOLYLINE) โดยปัดเศษภายใน tolerance ที่กำหนด ถ้าซ้ำกันสนิทให้เก็บไว้ 1 เส้นแล้วตัดที่เหลือทิ้ง

## 6. สิ่งที่เป็น "สัญญาณจริง" ที่ต้องตามหา

| ประเภทสัญญาณ | จะเจอที่ไหน | วิธีดึงมูลค่า |
|---|---|---|
| ตาราง Legend/Schedule (ประตู/หน้าต่าง/วัสดุ) | เลเยอร์ TEXT/MTEXT/TABLE ที่อยู่ใกล้ตารางกรอบสี่เหลี่ยม มักอยู่หน้าแรกหรือมุมแบบ | **อ่านเป็นตัวเลขที่มนุษย์เขียนไว้แล้ว — เชื่อถือได้มากกว่าการวัดจากรูปทรงเอง ใช้เป็นค่าอ้างอิงตรวจทาน** |
| ขอบเขตผนัง/ห้อง | closed LWPOLYLINE ที่พื้นที่อยู่ในช่วงสมเหตุสมผล (เทียบกับขนาดบ้านทั้งหลังที่รู้จากตารางพื้นที่ใช้สอย) | วัดพื้นที่ + หักช่องเปิดตาม SOP เดิม |
| ประตู/หน้าต่าง | block `INSERT` ที่อ้างชื่อ block ตรงกับรหัส D#/W# ในตาราง Legend | นับจำนวนครั้งที่ INSERT เกิดขึ้น ไม่ใช่วัดพื้นที่ block |
| งานโครงสร้าง (เสา/คาน) | เลเยอร์ COLUMN/COLM/Beam-1/Beam-2 ที่ตรงกับตาราง schedule เสา-คาน | จำนวนต้น/ความยาว x หน้าตัดจากตาราง ไม่ใช่วัดพื้นที่ปิดของเส้น |

**หลักการสำคัญที่สุด:** ตาราง Legend/Schedule ที่มนุษย์เขียนไว้ในแบบ (ที่ SOP เดิมกำหนดให้สแกนเก็บใน Step 3 ของ [03-ai-boq-procedure.md](./03-ai-boq-procedure.md)) คือ **แหล่งความจริงที่น่าเชื่อถือที่สุด** — เรขาคณิตดิบใช้ "ยืนยัน" ตัวเลขจากตาราง ไม่ใช่แหล่งความจริงเริ่มต้น เพราะเรขาคณิตดิบปนขยะเยอะเกินกว่าจะเชื่อได้ทันที

## 7. Heuristic ที่ใช้แยกได้จริง (ชื่อเลเยอร์เชื่อถือไม่ได้อย่างเดียว)

1. **Sanity range check ด้านพื้นที่** — ถ้าพื้นที่รวมของเลเยอร์หนึ่งมากกว่าพื้นที่ใช้สอยรวมทั้งหลัง (จากตาราง spec) เกิน 2-3 เท่า → ต้อง flag ไม่ใช่เชื่อ
2. **ตำแหน่ง Model Space vs Layout** — ตัดทิ้งทุกอย่างที่อยู่ใน Layout/Paper Space จากการคำนวณปริมาณ
3. **ประเภท entity vs ชนิด block** — INSERT ที่ชี้ไป block ในกลุ่มตกแต่ง (ชื่อ block มีคำว่า tree/car/human/shrub หรืออยู่ในโฟลเดอร์ block library ตกแต่งมาตรฐานของ ArchiCAD/AutoCAD) → ไม่นับ
4. **เทียบไขว้กับ Legend/Schedule** — ถ้าจำนวนที่นับได้จากรูปทรงไม่ตรงกับตัวเลขในตาราง ให้รายงานส่วนต่างเป็น "ข้อขัดแย้งที่ต้องตรวจสอบ" เสมอ ไม่ auto-resolve เอง
5. **เลเยอร์ที่ชื่อเป็นคำสงวนของ AutoCAD (`0`, `DEFPOINTS`) หรือมีคำที่บ่งบอกว่าเป็น annotation (`DIM*`, `TEXT*`, `TITLE*`, `GRID`, `Bodr*`, `FRAME*`)** — ตัดทิ้งจากการคำนวณปริมาณเสมอ เป็น default rule ที่ไม่ต้องเดา

## 11. รอบที่ 2: รัน [classify_layers.py](./project/code/python/classify_layers.py) เทียบทุกเลเยอร์/block กับ Exclusion + Category Schema พร้อมกัน — พบรูปแบบขยะใหม่ 3 แบบ

หลัง implement Layer Exclusion แล้ว เขียนสคริปต์เทียบ **ทุก** เลเยอร์/block ในไฟล์ (ไม่ใช่แค่ที่มี geometry) กับทั้ง denylist และ [04-category-schema.md](./04-category-schema.md) พร้อมกัน เจอสิ่งที่ยังไม่เคยบันทึกไว้:

### 11.1 เลเยอร์ที่ตั้งชื่อตามน้ำหนักเส้น (line-weight) ไม่ใช่ตามเนื้อหา
ไฟล์มีเลเยอร์ชื่อ `0.15`, `0.18`, `0.9`, `05`, `100` ฯลฯ — เป็นธรรมเนียมของบางโปรแกรม/บางสำนักที่ตั้งชื่อเลเยอร์ตาม **น้ำหนักเส้นตอนพิมพ์ (มม.)** ไม่ใช่ตามว่าเป็นผนัง/คาน/ท่ออะไร **เลเยอร์แบบนี้จะมีเนื้อหาอะไรก็ได้ปนกันหมด** — keyword matching ใช้ไม่ได้เลยเพราะชื่อไม่มีความหมายเชิงเนื้อหาตั้งแต่ต้น ต้องใช้ regex ตัดเป็นกลุ่มแยกต่างหาก (`^[0-9]+(\.[0-9]+)?$`) ไม่ใช่พยายามหา keyword ให้มัน

### 11.2 ชื่อ block/เลเยอร์ที่โปรแกรมสร้างเองอัตโนมัติ (ไม่ใช่ฝีมือดราฟต์แมน)
- Block ชื่อ `A$C` ตามด้วยเลขฐาน 16 (เช่น `A$C4E9B7405`) — เป็น anonymous/dynamic block ที่ AutoCAD สร้างเองภายใน (มักมาจาก hatch pattern หรือ associative dimension) ไม่ใช่เนื้อหาที่คนวาด
- Block ที่ขึ้นต้นด้วย `_` (เช่น `_Origin`, `_Open30`, `_Open90`, `_Oblique`, `_Dot`, `_DatumBlank`) — เป็น block มาตรฐานในตัวของ AutoCAD เอง (หัวลูกศร dimension ฯลฯ) โปรแกรมสร้างให้อัตโนมัติเสมอ
- Prefix อย่าง `ADCADD_`, `AUDIT_`, `AVE_` — ร่องรอยจากปลั๊กอิน/เครื่องมือซอฟต์แวร์ (AutoCAD DesignCenter, ODA File Converter ตอน audit-repair, ปลั๊กอิน render) ไม่ใช่เนื้อหาโปรเจกต์

ทั้งหมดนี้แก้ด้วย regex pattern ใน `EXCLUDED_LAYER_PATTERNS` ไม่ใช่ keyword เดี่ยวๆ เพราะเป็น "รูปแบบชื่อ" ไม่ใช่ "คำศัพท์"

### 11.3 ยืนยัน false positive จริงจาก keyword สั้น (ตามที่เคยเตือนไว้ใน §5 ข้อ 2)
ทดสอบจริงพบว่า `AC` (keyword หมวดปรับอากาศ) match เข้ากับ block ชื่อ `A$C69AC065E` โดยบังเอิญ และ `DB` (keyword หมวดไฟฟ้า) match เข้ากับ block ชื่อ `_ClosedBlank` (ตัวอักษร "dB" อยู่กลางคำ "closeDBlank") — ทั้งสองเป็น false positive ที่ไม่เกี่ยวอะไรกับหมวดที่ถูกจัดเข้าไปเลย

**แก้ด้วย token-aware matching:** keyword ที่สั้นกว่า 4 ตัวอักษรต้องแมตช์เป็น **prefix ของ token** (แยก token ด้วยอักขระที่ไม่ใช่ตัวอักษร/ตัวเลข เช่น `-`, `_`, ช่องว่าง, `$`) ไม่ใช่ substring ที่ไหนก็ได้ — ยังคงให้ `DIM` match กับ `DIMENSION`/`DIMS` ได้ปกติ (เป็น token เดียวกัน ไม่ใช่บังเอิญ) แต่ตัด false positive แบบ `AC`/`DB` ข้างบนออกไป ใช้ฟังก์ชันเดียว (`_token_aware_match` ใน `pynoi_parser.py`) ทั้งฝั่ง Layer Exclusion และ Category Schema matching เพื่อไม่ให้ตรรกะสองฝั่งเพี้ยนไปคนละทาง

## 12. รอบที่ 3: ตรวจสอบ INSERT/ATTDEF/spatial proximity จริง — พบว่า "ชื่อเลเยอร์ที่ block ถูก insert อยู่" เชื่อถือไม่ได้เลย

เจ้าของโปรเจกต์ยืนยันความหมายของ `FD-1`/`DR090SL1`/`CT002P`/`C805P` แล้ว (ดู [04-category-schema.md](./04-category-schema.md) หมวด 2.4/3.4/3.5) ระหว่างตรวจสอบเพื่อตอบคำถาม "รหัสพวกนี้ถูกกำกับความหมายไว้ที่ไหนในไฟล์" พบ 2 เรื่องสำคัญที่ต้องบันทึกแยกจากคำศัพท์รายตัว เพราะกระทบสถาปัตยกรรมทั้งระบบ:

### 12.1 ⚠️ ห้ามใช้ "เลเยอร์ที่ block ถูก insert อยู่" ตัดสินว่า block นั้นคือขยะหรือสัญญาณ

ตรวจสอบด้วย `doc.modelspace()` แล้วพบว่า block product จริง (ยืนยันแล้วว่าเป็น COTTO/ประตูจริง) ถูกวางไว้บนเลเยอร์ที่ชื่อไม่เกี่ยวอะไรกับตัวมันเลย:

| Block (ยืนยันแล้วว่าเป็นสัญญาณจริง) | Insert อยู่บนเลเยอร์ |
|---|---|
| `CT002P` (สุขภัณฑ์ COTTO) | `WALL` |
| `C805P` (สุขภัณฑ์ COTTO) | `DIM` (!) |
| `DR090SL1` (ประตู) | `DIM` (!) |

เลเยอร์ `DIM` คือเลเยอร์ที่ Layer Exclusion ตัดทิ้งทั้งหมดในปัจจุบัน (คิดว่ามีแต่เส้นบอกระยะ) — **ถ้าวันหนึ่งมีคนเขียนโค้ดนับจำนวนประตู/สุขภัณฑ์จาก INSERT entity โดยกรองด้วยเลเยอร์ก่อน (เหมือนที่ทำกับ LINE/TEXT ใน Layer Exclusion ตอนนี้) จะทำให้ของจริงหายไปจาก BOQ เงียบๆ**

**กฎที่ต้องยึดเมื่อ implement การนับ block/fixture ในอนาคต:** Layer Exclusion (§5.2) ใช้ได้กับ entity ที่ไม่มีอัตลักษณ์ของตัวเอง (LINE, TEXT, HATCH, DIMENSION — เชื่อชื่อเลเยอร์เป็นหลักเพราะไม่มีข้อมูลอื่นให้เชื่อ) **แต่ INSERT (block reference) ต้องตัดสินจากชื่อ block เท่านั้น ห้ามกรองด้วยเลเยอร์ที่มันถูกวางอยู่เด็ดขาด** เพิ่มเป็น `entity_type_warning` ใน `matching_rules` ของ [04-category-schema.md](./04-category-schema.md) แล้ว — ยังไม่ใช่บั๊กในโค้ดปัจจุบัน (เพราะ `pynoi_parser.py` ยังไม่นับ INSERT เป็นปริมาณเลย) แต่เป็นกับดักที่ต้องรู้ล่วงหน้าก่อนไป implement Step 6/7 เต็มรูปแบบ

### 12.2 ไฟล์ CAD ไม่ได้ self-document ทุกอย่าง — ต้องมี vocabulary ภายนอก

ตรวจ block definition ของ `CT002P` พบว่ามีแค่เส้น/โค้ง ไม่มี ATTDEF อธิบายเลย ส่วน `C805P` มี ATTDEF `SERIAL` = `"C805"` (แค่เลขซีเรียล ไม่ใช่ชื่อสินค้า) และค้นทั้งไฟล์ไม่เจอ text ที่พิมพ์คำว่า "CT002P"/"C805P" ตรงๆ ที่ไหนเลย มีแค่ MTEXT บอกชื่อรุ่นแบบหลวมๆ (`COTTO DOS MEDIA`, `COTTO DOS FLEX 100`) วางอยู่ในบริเวณใกล้เคียงกลุ่ม block (ห่างกัน ~20-30 หน่วย ไม่ใช่ตำแหน่งเดียวกันเป๊ะ และไม่มี link ทาง data ใดๆ ผูกกับ block ที่เจาะจง)

## 13. "ล้างไฟล์ก่อนค่อยถอดแบบ" — implement แล้วเป็น [clean_dxf.py](./project/code/python/clean_dxf.py)

เจ้าของโปรเจกต์ถามว่าควร **ล้างไฟล์ CAD ให้เป็นไฟล์ใหม่ที่สะอาดก่อน** แล้วค่อยถอดแบบจากไฟล์นั้น แทนที่จะกรองแบบ in-memory ทุกครั้งที่รันเหมือนตอนนี้ — คำตอบคือ **ทำทั้งสองอย่างคู่กัน ไม่ใช่เลือกอย่างใดอย่างหนึ่ง:**

  2. **คือ deliverable ของบริการ "CAD Cleanup Fee"** ที่ออกแบบไว้ใน [02-business-model-finance.md](./02-business-model-finance.md) พอดี — ไฟล์นี้คือสิ่งที่ส่งกลับให้ลูกค้าได้ตรงๆ
  3. เป็นจุดตรวจสอบ (checkpoint) ก่อนเข้าสู่ขั้นตอนคำนวณที่ซับซ้อนกว่า (net deduction) — ถ้าไฟล์สะอาดผิดจากที่คาด รู้ตัวเร็วกว่า

**อัปเดต (2569-08-23):** เพิ่ม **Duplicate Purge** (ลบ LINE/LWPOLYLINE ที่ซ้ำกันสนิทบนเลเยอร์เดียวกัน — ตรงกับที่ขอให้ "ลบคำซ้ำๆ") เข้า `clean_dxf.py` เป็น pass ที่ 2 แล้ว รันจริงพบว่า**ลบซ้ำได้ 300 entity แต่พื้นที่เลเยอร์ `WALL` แทบไม่ขยับ (289,034.51 → 289,033.50 ตร.ม.)** สรุปตรงๆ ว่า Duplicate Purge ไม่ใช่คำตอบของปัญหา WALL — ของที่ปนอยู่ไม่ใช่เส้นซ้ำกัน แต่เป็นรูปปิดที่ต่างกันจริงหลายรูป (hatch/detail loop คนละรูปทรง) ปนกันอยู่ในเลเยอร์เดียว ต้องใช้ Bounding Box Filter หรือ logic แยก "ขอบเขตห้อง/ผนังจริง" ออกจาก loop ย่อยอื่นๆ ต่อไป ไม่ใช่แค่ตัดของซ้ำ

**สิ่งที่ทำ (entity-type-aware ตาม §12.1):** ลบเฉพาะ entity ที่ผ่านเกณฑ์ Layer Exclusion จริง — entity ทั่วไป (LINE/TEXT/HATCH/ฯลฯ) ตัดสินจากชื่อ**เลเยอร์**, ส่วน INSERT ตัดสินจากชื่อ**block** เท่านั้น (ไม่แตะเลเยอร์ที่มันถูกวางอยู่) **ไม่แตะอะไรที่ยังอยู่ใน `pending_review`** — ไม่แน่ใจ = ไม่ลบ

**ผลจากการรันจริงกับ `newhouse 2569.dxf`:** ลบไป 6,300 จาก 18,043 entity (~35%) — 6,121 จากการกรองด้วยเลเยอร์ + 179 จากชื่อ block ที่รู้แล้วว่าเป็นของตกแต่ง ขนาดไฟล์ลดจาก 21.6MB → 18.6MB

⚠️ **ข้อจำกัดที่ต้องรู้ — การล้างรอบนี้ไม่ได้แก้ปัญหาใหญ่ที่สุด:** รันตรวจซ้ำหลังล้างแล้ว เลเยอร์ `WALL` ยังคงคำนวณพื้นที่ได้ 289,034.51 ตร.ม. เท่าเดิมทุกประการ — เพราะ `WALL` ไม่ได้อยู่ใน exclusion list (มันคือเลเยอร์ที่ถูกต้อง มีของจริงปนอยู่) ปัญหาจริงคือ hatch/detail loop ปนอยู่ *ในเลเยอร์เดียวกัน* กับผนังจริง ซึ่งเป็นปัญหาระดับเรขาคณิต (ต้องใช้ Duplicate Purge + Bounding Box Filter ตาม §5.1/§5.3) ไม่ใช่ปัญหาระดับชื่อเลเยอร์ที่ clean_dxf.py แก้ได้ — **การล้างไฟล์รอบนี้เป็นก้าวที่ดีและควรทำ แต่ยังไม่ใช่ก้าวสุดท้ายก่อนจะถอดแบบได้แม่นยำจริง**

**สรุป: รหัสประเภทนี้ไม่มีทางถูก auto-resolve จากไฟล์ CAD เพียงไฟล์เดียวได้** ต้องอาศัยความรู้ภายนอก (แคตตาล็อกสินค้า/ประสบการณ์ผู้ใช้) เป็นแหล่งความจริง — นี่คือเหตุผลที่ต้องมีระบบ [09-vocabulary-review-workflow.md](./09-vocabulary-review-workflow.md) แยกต่างหากจากการพยายามอ่าน legend ในแบบอัตโนมัติอย่างเดียว (Step 3 ของ SOP ยังมีประโยชน์สำหรับ legend ที่เขียนไว้จริงๆ เช่นตาราง F1-F4/D1-D5 แต่ใช้ไม่ได้กับรหัสสินค้าที่อ้างอิงจาก block library ภายนอก)

## 14. ⚠️ กลับหลักการ: ต้องมี "หลักฐานสนับสนุน" ก่อนถึงจะนับเป็นสัญญาณ ไม่ใช่นับไว้ก่อนแล้วค่อยพิสูจน์ว่าเป็นขยะ

หลังไล่ยืนยันรหัส COTTO ทีละตัว (§12) เจ้าของโปรเจกต์ทักท้วงสำคัญ: **ไล่ยืนยันทีละรหัสแบบนี้ไม่ scale ข้ามโครงการ** — โครงการอื่น บริษัทอื่น ก็มีรหัสของตัวเองอีกชุดที่ไม่มีวันไล่ทันหมด และยกตัวอย่างจริงที่พลิกสมมติฐานเดิม: `ct0150p` อยู่บนเลเยอร์ `DIM` เหมือน `C805P` ที่ยืนยันแล้วว่าเป็นสัญญาณจริง — แต่ `ct0150p` กลับเป็น**ความผิดพลาดของดราฟต์แมนคนหนึ่งที่วางผิดเลเยอร์เฉยๆ** (พนักงานคนนั้นถูกให้ออกจากงานไปแล้วเมื่อ 2 เดือนก่อน) ข้อความรอบๆ ก็ไม่ใช่ชื่อสินค้า (แค่ "MH." = ชื่อโครงการย่อ, "RK" ที่ไม่มีความหมาย, ตัวเลขบอกระยะ) — **สิ่งเดียวกันทุกประการ (อยู่บนเลเยอร์เดียวกัน) เป็นได้ทั้งสัญญาณจริงและขยะ ขึ้นอยู่กับว่าใครวาง**

**หลักที่เจ้าของโปรเจกต์วางไว้:** *"คุณ (AI) เห็นลึกกว่ามนุษย์มาก แต่ถ้ามนุษย์มองแล้วไม่เห็นว่ามันเกี่ยวข้อง ก็แปลว่าไม่ต้องนับเข้า BOQ"* — นี่คือการกลับทิศของภาระการพิสูจน์ (burden of proof):

- **แนวทางเดิม (ไม่ scale):** เจอ block/เลเยอร์แปลกๆ → พยายามสืบจนกว่าจะรู้ว่ามันคืออะไร → ถ้าไม่รู้ก็ปล่อยผ่านเป็น "ไม่แน่ใจ" ไปเรื่อยๆ ทีละไฟล์ ทีละโครงการ ไม่มีวันจบ
- **แนวทางใหม่ (scale ได้):** **ทุกอย่าง default เป็น "ไม่นับ" จนกว่าจะมีหลักฐานสนับสนุนเพียงพอ** — ไม่ต้องรู้ว่ามันคือ "อะไร" เป๊ะ (ไม่ต้องรู้ว่า `C812F` คือรุ่นราวผ้ารุ่นไหนของ COTTO) แค่ต้องมีหลักฐานอย่างน้อย 1 ข้อร่วมกัน ถึงจะยกระดับเป็น "นับ":
  1. **ตรงกับตาราง Legend/Schedule** ที่มนุษย์เขียนไว้ในแบบ (จำนวน/ประเภทตรงกัน) — น้ำหนักมากที่สุด
  2. **มีข้อความบรรยายที่ชัดเจนอยู่ใกล้ๆ** (เช่น "TOWEL BAR" ที่เจอกับ `C812F`) ไม่ใช่แค่ตัวเลขบอกระยะหรือคำย่อโครงการ
  3. **รูปแบบการวางซ้ำที่สม่ำเสมอ** (เช่นคู่ block เดิมปรากฏซ้ำๆ ในตำแหน่งที่สมเหตุสมผลหลายจุดทั่วบ้าน)
  4. ถ้าไม่มีข้อไหนเลย (เหมือน `ct0150p`) → **ไม่นับ ไม่ต้องรู้ว่ามันคืออะไร ไม่ต้องไล่สืบต่อ**

**ผลลัพธ์ต่อวิธีทำงาน:** เลิกไล่ยืนยันรหัสสินค้าทีละตัวแบบ §12 เป็นแนวทางหลัก — ใช้ 4 ข้อข้างบนเป็นเกณฑ์อัตโนมัติ/กึ่งอัตโนมัติแทน ปิดกลุ่ม `confirmed_brand_product_codes` ใน [04-category-schema.md](./04-category-schema.md) ด้วยเกณฑ์นี้ทีเดียวแทนการไล่ทีละตัว (ดู `closed_out_2569-08-23` ในไฟล์นั้น) — **นี่คือสิ่งที่ทำให้ระบบนี้ใช้ได้กับโครงการ/บริษัทอื่นจริง** เพราะไม่ต้องรู้จักรหัสของทุกบริษัทล่วงหน้า แค่ต้องมีกฎเรื่อง "หลักฐานเพียงพอ" ที่ใช้ร่วมกันได้ทุกที่

**Implement เป็นโค้ดแล้ว:** [evidence_score.py](./project/code/python/evidence_score.py) ทำข้อ 2-3 (ยังไม่ทำข้อ 1 — ต้องรอ legend parsing) ⚠️ **ทดสอบแล้วพบข้อจำกัดจริง:** เอา `ct0150p` (ที่ยืนยันแล้วว่าเป็นความผิดพลาด) มาทดสอบ ระบบกลับให้ผล "likely_signal" ผ่านเกณฑ์ข้อ 3 เพราะมันถูกวางซ้ำ 12 ครั้งบนเลเยอร์เดียวกันสม่ำเสมอ **เหมือนของจริงทุกประการ** — ดราฟต์แมนคนนั้นทำผิดแบบเดิมซ้ำๆ ไม่ใช่ทำผิดครั้งเดียว เกณฑ์ 2-3 เลยแยกไม่ออกจริงๆ ในเคสนี้ **สรุป: เกณฑ์ 2-3 ช่วยกรองขยะชัดๆ ออกได้ (เช่น `B-3` ที่ไม่มีอะไรสนับสนุนเลย) แต่กรณีก้ำกึ่งยังต้องให้คนยืนยันอยู่ดี ไม่ใช่ auto-apply — เกณฑ์ข้อ 1 (จับคู่กับ Legend/Schedule) เท่านั้นที่จะปิดช่องว่างนี้ได้จริง**

## 15. ⚠️ แก้ไขสำคัญ: "ไม่เกี่ยวกับ BOQ" ≠ "ไม่เกี่ยวกับแบบ" — สรุปเรื่องการกรองใหม่ทั้งหมด

เจ้าของโปรเจกต์ทักท้วง (2569-08-23): `clean_dxf.py` ที่ผ่านมาลบเลเยอร์อย่าง `DIM`/`GRID`/`TITLE`/`SPEC`/`HATCH`/block ตกแต่งออกจากไฟล์จริง โดยคิดว่าสิ่งเหล่านี้ "ไม่เกี่ยวข้อง" — **แต่มันเกี่ยวข้องกับตัวแบบ (drawing) จริงๆ แค่ไม่เกี่ยวกับ BOQ เท่านั้น** เส้นบอกขนาด เส้นกริด กรอบชื่อเรื่อง หมายเหตุสเปก ลายวัสดุ แม้แต่ต้นไม้ในผังบริเวณ ล้วนเป็นสิ่งที่ดราฟต์แมนตั้งใจใส่ไว้เพื่อให้แบบสมบูรณ์/อ่านเข้าใจได้ — การลบทิ้งจากไฟล์จริงคือการทำลายแบบ ไม่ใช่แค่ "ทำความสะอาด"

**โครงสร้างใหม่ที่แก้แล้ว — แยกเป็น 2 ระดับชัดเจนใน [04-category-schema.md](./04-category-schema.md) `exclusion_rules`:**

| ระดับ | ใช้ทำอะไร | ตัวอย่าง | ลบออกจากไฟล์ไหม |
|---|---|---|---|
| `quantity_exclusion` | **ข้าม** ตอนรวมปริมาณ BOQ (ยังเป็นเนื้อหาจริงของแบบ) | DIM, GRID, TITLE, SPEC, HATCH, TABLE, TEXT, ต้นไม้/รถ/เฟอร์นิเจอร์ตกแต่ง, เลเยอร์ `0`, เลเยอร์ตั้งชื่อตามน้ำหนักเส้น | **ไม่ลบเด็ดขาด** |
| `safe_to_delete` | ลบออกจากไฟล์ได้จริง (ไม่มีข้อมูลอะไรสูญหายเลย) | `DEFPOINTS` (ยืนยันแล้วว่า non-plotting เสมอ ไม่มีใครเห็น), block/เลเยอร์ที่ AutoCAD/ปลั๊กอินสร้างเองอัตโนมัติ (`A$C...`, `_Origin` ฯลฯ, `ADCADD_`/`AUDIT_`/`AVE_`) | ลบได้ — เป็นแค่ขยะซอฟต์แวร์ ไม่ใช่ฝีมือคน |

**ผลจากการแก้ใน `clean_dxf.py`:** ก่อนแก้ลบไป 6,600 entity (เยอะเกินจริง รวมของจริงในแบบไปด้วย) **หลังแก้เหลือลบแค่ 787 entity** (48 จากเลเยอร์ software-internal เช่น DEFPOINTS, 130 จาก block software-internal, ที่เหลือ 609 คือ Duplicate Purge ของซ้ำจริงๆ) — ตรวจซ้ำแล้วยืนยันว่า `DIM`/`GRID`/`SPEC` **ยังอยู่ในไฟล์ที่ล้างแล้วครบถ้วน** (แค่ไม่ถูกนับเป็นปริมาณ BOQ เท่านั้น)

**สรุปสั้นๆ ให้จำง่าย:** ไฟล์ "cleaned" ตอนนี้ = ไฟล์เดิมเกือบทั้งหมด ลบแค่ขยะซอฟต์แวร์ + ของซ้ำจริงๆ ส่วนการ "ข้ามไม่นับ" สำหรับ BOQ เป็นคนละขั้นตอน (เกิดตอนคำนวณปริมาณใน `pynoi_parser.py`/`classify_layers.py` เท่านั้น ไม่ใช่ตอนล้างไฟล์)

## 16. Duplicate Purge เดิมไม่ครอบคลุม TEXT/MTEXT — เพิ่มให้แล้ว

เจ้าของโปรเจกต์ถามว่า "คำเดิมๆ ซ้ำกันในตำแหน่งเดิม (เช่น ป้ายบอกขนาดท่อน้ำ) อยู่ขั้นตอนไหน" — ตรวจแล้วพบว่า **Duplicate Purge (Pass 2) เดิมเช็คแค่ LINE/LWPOLYLINE ไม่ได้แตะ TEXT/MTEXT เลย** เป็นช่องโหว่จริง เพิ่มเข้าไปแล้ว: ป้ายข้อความจะถือว่าซ้ำก็ต่อเมื่อ **ทั้งคำและตำแหน่งตรงกันเป๊ะ** เท่านั้น

⚠️ **ข้อควรระวังสำคัญที่ต้องแยกให้ออก:** ป้าย "CW Ø3/4"" ที่ปรากฏหลายจุดทั่วบ้าน **ไม่ใช่ของซ้ำ** แม้คำจะเหมือนกัน เพราะแต่ละจุดคือท่อน้ำคนละเส้นจริงที่บังเอิญขนาดเท่ากัน (ต้องนับทุกจุดแยกกันตอนถอดปริมาณ) — Duplicate Purge จะลบให้ก็ต่อเมื่อคำ **และ** ตำแหน่งตรงกันเป๊ะเท่านั้น (เช่น ป้ายเดิมถูก copy วางทับตัวเอง)

**ทดสอบแล้ว:** รันกับ `newhouse 2569.dxf` พบว่า**ไม่มี TEXT/MTEXT ที่ซ้ำกันจริงในไฟล์นี้เลย** (0 รายการ) — โค้ดใหม่พร้อมใช้งาน แต่ไฟล์นี้บังเอิญไม่มีเคสให้ทดสอบจริง ต้องรอไฟล์อื่นที่มีปัญหานี้จริงถึงจะเห็นผล

## 17. เพิ่ม 2 pass ใหม่ (opt-in): มาตรฐานฟอนต์ + purge เลเยอร์ไม่ใช้

เจ้าของโปรเจกต์ขอเพิ่มการล้าง 3 เรื่องหลังตรวจไฟล์ cleaned รอบแรก (ที่มาจากพฤติกรรมมักง่ายของดราฟต์แมนที่ถูกให้ออกไปแล้ว — copy/paste ยำมาหลายไฟล์):

### 17.1 มาตรฐานฟอนต์ (`--standardize-font`)
ตรวจไฟล์จริงพบหลักฐานยืนยันชัดเจนตามที่สงสัย — **66 text style ใช้ฟอนต์ต่างกันเป็นสิบแบบ**: `CordiaUPC.ttf` ถูกผูกกับชื่อ style ต่างกันเกือบสิบชื่อ (`S50`, `S100`, `B`, `S25`, ...), มี `.shx` ปนหลายแบบ (`angsana.shx`, `thai2.shx`, `master.shx`), มีแม้แต่ path เพี้ยนๆ อย่าง `C:\AECPLUS/fonts/SIMPLEX` และ `-DB 75 Narai` ที่ดูเหมือนอ้างอิงพัง — เพิ่มฟังก์ชัน `standardize_fonts()` เซ็ตทุก style ให้ชี้ไปที่ฟอนต์เดียวกัน โดยไม่ยุบ/เปลี่ยนชื่อ style (กัน entity ที่อ้างอิง style เดิมพัง)

ลองรอบแรกด้วย `THSarabunPSK.ttf` (66/66 style) แต่เจ้าของโปรเจกต์แจ้งว่าไม่มีฟอนต์นี้ในเครื่องจริง (คำตอบก่อนหน้าที่บอกว่ามีนั้นคลาดเคลื่อน) — เปลี่ยนเป็น `CordiaUPC.ttf` แทนตามคำขอ (มีอยู่แล้วในไฟล์เดิมมากที่สุด) รันจริง: **66/66 style เปลี่ยนเป็น CordiaUPC.ttf หมด** (47 style เปลี่ยนจริง อีก 19 style ใช้ฟอนต์นี้อยู่แล้วตั้งแต่ต้น) บันทึกอยู่ที่ `newhouse 2569.cleaned.v2.dxf`

### 17.2 Purge เลเยอร์ที่ไม่ได้ใช้ (`--purge-layers`)
เช็คการใช้งานจริงข้าม modelspace + ทุก paperspace layout + ทุก block definition (เผื่อเลเยอร์ถูกใช้แค่ใน block) ลบเฉพาะเลเยอร์ที่ไม่มี entity ไหนอ้างอิงเลยจริงๆ (ยกเว้นเลเยอร์ `0` ที่ AutoCAD บังคับให้มีเสมอ) รันจริงแล้ว: **ลบได้ 28 เลเยอร์** (เช่น `ASHADE`, `SPACE`, `STAIR`, `HACTH`, `บ้าน`, `ลำน้ำ`) — ตรงกับที่สงสัยว่าเป็นเลเยอร์ที่ติดมาจากไฟล์โครงการอื่นแล้วไม่เคยถูกใช้จริงในไฟล์นี้

### 17.2b Purge text style ที่ไม่ได้ใช้ (`--purge-styles`)
เจ้าของโปรเจกต์ถามต่อว่า "purge style ที่ไม่ได้ใช้มีไหม" — เพิ่มให้แล้ว ใช้ตรรกะเดียวกับ purge เลเยอร์: เช็ค TEXT/MTEXT/ATTDEF/ATTRIB ทุกตัว **รวมถึง `dimtxsty` ของทุก DIMSTYLE ด้วย** (เพราะ style อาจ "ถูกใช้" อยู่แค่ในระบบ dimension โดยไม่มี TEXT ตรงๆ อ้างอิงเลย) ลบเฉพาะที่ไม่มีอะไรอ้างอิงจริง (ยกเว้น `STANDARD` ที่ AutoCAD บังคับให้มีเสมอ) รันจริง: **ลบได้ 11 style ที่ไม่ใช้** (เช่น `GOST-2.304_Type-B` 3 ตัวที่ไม่มี font เลยด้วยซ้ำ, `CORDIAUPC`, `th100`) เหลือ 55 style ที่ standardize_fonts() ต้องแก้ไขจริงๆ (ลดงานลงจาก 66)

⚠️ **ทั้งสาม pass นี้เป็น opt-in (ปิดโดย default)** ต้องระบุ flag ชัดเจนถึงจะทำงาน เพราะเป็นการแก้ไขเนื้อหาแบบ (เปลี่ยนฟอนต์/ลบเลเยอร์/ลบ style) ไม่ใช่แค่คัดกรองขยะแบบ Pass 1-2

### 17.3 ⚠️ บั๊กสำคัญที่พบ: แก้ style table แล้วฟอนต์ยังไม่เปลี่ยนจริง — MTEXT มี font override ฝังอยู่ในเนื้อความเอง

ส่งไฟล์ v3 ให้ตรวจ เจ้าของโปรเจกต์เปิดใน GstarCAD แล้วพบว่า**ข้อความบางส่วนยังเป็นตัวอักษรไทยที่แตกเป็นชิ้นๆ อ่านไม่ออก** ทั้งที่ style table ยืนยันแล้วว่าเป็น CordiaUPC.ttf ครบทุก style — ตรวจสอบพบสาเหตุจริง:

**MTEXT สามารถฝังคำสั่งเปลี่ยนฟอนต์ไว้ในเนื้อความของตัวเองได้** (`{\fTH SarabunPSK|b0|i0|c222|p34;ข้อความ}`) ซึ่ง**มีผลเหนือกว่า font ที่ style table กำหนดไว้** — `standardize_fonts()` แก้แค่ style table เลยไม่มีผลกับข้อความกลุ่มนี้เลย

ตรวจทั้งไฟล์พบ **179 MTEXT ที่ฝัง font override แบบนี้ไว้ อ้างอิงฟอนต์ต่างกันถึง 7 แบบ** (`TH SarabunPSK`, `LilyUPC`, `AngsanaUPC`, `Vrinda`, `Cordia New`, `Angsana New`, `FreesiaUPC`) — ที่แตกเป็นชิ้นในภาพที่เจ้าของโปรเจกต์ส่งมาคือข้อความที่ฝัง `TH SarabunPSK` ไว้พอดี (ฟอนต์ที่เครื่องเจ้าของโปรเจกต์ไม่มีติดตั้ง) พอ GstarCAD หาฟอนต์ไม่เจอเลยแสดงผลตัวอักษรไทยเพี้ยน

**แก้แล้ว:** เพิ่ม `strip_inline_font_overrides()` ลบคำสั่ง `\f...;` ที่ฝังอยู่ออกทั้งหมด (ไม่ใช่เปลี่ยนชื่อฟอนต์ในคำสั่ง แต่ลบคำสั่งทิ้งไปเลย) ข้อความจะกลับไปใช้ฟอนต์ตาม style ของตัวเอง (ที่ standardize_fonts() ตั้งไว้แล้ว) — รันคู่กับ `--standardize-font` เสมอ (ไม่ใช่ pass แยก เพราะจุดประสงค์เดียวกัน) รันจริง: **ลบได้ครบ 179/179 จุด** ตรวจซ้ำแล้วว่าไม่มี inline font code เหลือเลย ได้ไฟล์ `newhouse 2569.cleaned.v4.dxf`

**บทเรียน:** การตรวจสอบด้วยโค้ด (`doc.styles` ทุกตัวเป็น CordiaUPC.ttf ✓) ไม่พอที่จะสรุปว่า "ฟอนต์ถูกต้องหมดแล้ว" — ต้องเปิดดูด้วยตาจริงในโปรแกรม CAD เสมอ (ตรงกับเหตุผลที่สร้าง `clean_dxf.py` ให้ materialize เป็นไฟล์จริงตั้งแต่แรก ไม่ใช่แค่เชื่อ log)

### 17.4 เรื่อง plot style (`monochrome.ctb`) — ยังไม่ได้แก้ เพราะไฟล์นี้ตั้งไว้ถูกอยู่แล้ว
ตรวจ `current_style_sheet` ของทั้ง 2 layout (`Model`, `Layout1`) พบว่า **ตั้งเป็น `monochrome.ctb` อยู่แล้วทั้งคู่** ตรงกับที่ขอพอดี — ยังไม่พบปัญหาที่ต้องแก้ในไฟล์นี้ ⚠️ ที่เจ้าของโปรเจกต์พูดถึง `.clb` ไม่ใช่นามสกุลมาตรฐานของ AutoCAD (ปกติเป็น `.ctb`/`.stb`) — อาจพิมพ์ผิด หรือหมายถึงการตั้งค่าอื่น (เช่น printer/plotter config `.pc3`) ต้องถามเพิ่มก่อนจะแก้อะไรต่อ

### 17.5 ปัญหาชื่อไฟล์ทับกัน — เพิ่ม auto-versioning แล้ว
ส่งไฟล์ cleaned ให้ตรวจ 2 รอบด้วยชื่อเดิม (`*.cleaned.dxf` ถูกเขียนทับทุกครั้งที่รัน) ทำให้เจ้าของโปรเจกต์แยกไม่ออกว่าไฟล์ที่เปิดอยู่เป็นเวอร์ชันที่มีฟอนต์แก้แล้วหรือยัง — เปลี่ยน default output ให้ auto-version เป็น `<name>.cleaned.v1.dxf`, `.v2.dxf`, ... (หาเลขเวอร์ชันสูงสุดที่มีอยู่ในโฟลเดอร์แล้ว +1 ให้เอง) **ไม่เขียนทับของเก่าอีกต่อไป** เทียบก่อน-หลังได้ตลอด — เพิ่ม pattern `*.cleaned.v*.dxf` เข้า `.gitignore` ด้วย (ยังเป็น derived artifact ไม่ commit เหมือนเดิม)
