# ระบบสอนคำศัพท์ให้ "ไพน้อย" โดยไม่ต้องแก้โค้ด

> เกิดจากคำถามของเจ้าของโปรเจกต์: "แต่ละบริษัท/ผู้รับเหมาเขียนแบบไม่ตรงกันหรือไม่มาตรฐาน จะแก้ปัญหานี้ยังไงต่อไป ให้ไพน้อยรู้จักโดยไม่ต้องแก้ไข code หรือทำสำรวจแล้วไม่รู้ให้ถามก่อน หรืออะไรที่ลดภาระได้"

## 1. หลักการ: ข้อมูล ≠ โค้ด แยกกันเด็ดขาด

ทุกอย่างที่ "ไพน้อย" ต้องรู้จัก (คำศัพท์ที่เป็นสัญญาณ, คำศัพท์ที่เป็นขยะ) อยู่ใน [04-category-schema.md](./04-category-schema.md) ทั้งหมด — เป็น **ข้อมูล (JSON)** ไม่ใช่โค้ด Python ทั้ง `pynoi_parser.py` และ `classify_layers.py` โหลด schema นี้ตอนรันทุกครั้งผ่าน [schema_loader.py](./project/code/python/schema_loader.py) **ไม่มี keyword ไหนถูก hardcode ไว้ในไฟล์ .py เลย** — เพิ่มคำศัพท์ = แก้ไฟล์ markdown เดียว ไม่ต้องแตะโค้ด

## 2. ปัญหาที่เหลือ: การแก้ JSON เองก็ยังเป็นภาระ

แม้ไม่ต้องแก้โค้ดแล้ว การเปิด `04-category-schema.md` ไปหาตำแหน่งที่ถูกต้องแล้วพิมพ์ JSON ให้ syntax ถูกต้องเองก็ยังเป็นภาระ (พิสูจน์แล้วจริงระหว่างพัฒนา — ตอนเขียนสคริปต์ apply อัตโนมัติ เผลอทำ JSON พังเพราะ backslash หลุดหาย ต้องแก้ด้วยมือ) **เจ้าของโปรเจกต์ไม่ควรต้องแก้ JSON เองเลย**

## 3. ทางแก้: วงจร "สแกน → กรอกตาราง → apply อัตโนมัติ"

```
1. รัน classify_layers.py กับไฟล์ CAD ใหม่
      ↓
2. คำที่ไม่รู้จัก (ไม่ตรงทั้ง exclusion และ category) ถูกเติมเข้า
   vocabulary_review.csv โดยอัตโนมัติ (ไฟล์ CSV เปิดด้วย Excel ได้ตรงๆ)
      ↓
3. เจ้าของโปรเจกต์เปิดไฟล์ CSV — กรอกแค่ 3 คอลัมน์สำหรับแถวที่ status=pending:
      target_category  (เช่น "3.4" หรือ "3" ถ้าจะจัดเป็นสัญญาณ, เว้นว่างถ้า exclude)
      action            (classify / exclude / ignore)
      status            (เปลี่ยนจาก pending → confirmed)
      ↓
4. รัน apply_vocabulary_review.py — merge เข้า 04-category-schema.md ให้อัตโนมัติ
   (เขียน JSON ให้ถูก syntax เอง) แล้ว mark แถวเป็น applied
```

**เจ้าของโปรเจกต์ไม่ต้องแตะ JSON หรือโค้ดเลยตลอดวงจรนี้** — งานที่ต้องทำคือกรอกตาราง Excel 3 ช่องต่อคำเท่านั้น เหมือนกับที่คุ้นเคยอยู่แล้วจากการทำ BOQ

## 4. รูปแบบไฟล์ `vocabulary_review.csv`

| คอลัมน์ | ใครกรอก | ความหมาย |
|---|---|---|
| `term` | ระบบ | คำ/รหัสที่เจอ |
| `kind` | ระบบ | `layer` หรือ `block` |
| `first_seen_file` / `last_seen_file` | ระบบ | ไฟล์ที่เจอครั้งแรก/ล่าสุด |
| `times_seen` | ระบบ | เจอกี่ครั้งสะสม (ทุกไฟล์ที่เคยสแกน) |
| `target_category` | **คุณ** | รหัสหมวด เช่น `3.4` (เว้นว่างถ้า action=exclude/ignore) |
| `action` | **คุณ** | `classify` / `exclude` / `ignore` |
| `status` | **คุณ** | เปลี่ยนเป็น `confirmed` เมื่อกรอกเสร็จ (ระบบจะเปลี่ยนเป็น `applied` เองหลัง apply) |
| `notes` | คุณ (ไม่บังคับ) | บันทึกเหตุผล/ที่มา |

**สำคัญ:** ไฟล์นี้เป็น worklist สะสม ไม่ถูกเขียนทับทุกครั้งที่สแกน — คำที่เคยตัดสินใจแล้ว (`applied`) จะไม่ถูกถามซ้ำ แม้ไฟล์ CAD โปรเจกต์ใหม่จะมีคำนั้นอีก (ยกเว้นจะเจอคำ**ใหม่**ที่ไม่เคยเห็น ถึงจะเพิ่มแถวใหม่)

## 5. ทำไมวิธีนี้ตอบโจทย์ "แต่ละบริษัทเขียนแบบไม่ตรงกัน" ได้จริง

- ไม่มีทางเขียน keyword ให้ครอบคลุมทุกบริษัทได้ล่วงหน้า — ธรรมชาติของปัญหานี้คือ "เจอทีหลังรู้ทีหลัง" เสมอ ระบบนี้ยอมรับความจริงข้อนี้แทนที่จะพยายามแก้ไม่ให้เกิด
- ทุกครั้งที่ตอบคำถามใหม่ 1 คำ **ไพน้อยฉลาดขึ้นถาวรสำหรับทุกโปรเจกต์ในอนาคต** ไม่ใช่แค่โปรเจกต์นี้ — ตรงกับแนวคิด Data Flywheel ที่วางไว้สำหรับรักบ้าน@CNX ด้วย (ยิ่งทำงานเยอะยิ่งฉลาด)
- รหัสสินค้าเฉพาะทาง (เช่น COTTO codes) ที่ไฟล์ CAD เองไม่ได้กำกับความหมายไว้เลย (ดู [04-category-schema.md](./04-category-schema.md) หมวด 3.5 — ตรวจสอบแล้วว่า `CT002P` ไม่มี attribute/text อธิบายในไฟล์เลย) **ก็ยังจัดการได้** ผ่านระบบนี้ เพราะไม่ต้องพึ่งพาให้ไฟล์ CAD self-document ทุกอย่าง

## 6. "ไม่รู้ให้ถามก่อน" — สถานะปัจจุบันกับเป้าหมายปลายทาง

**ตอนนี้:** classify_layers.py "ถาม" ผ่านการเติมแถวใน CSV (passive — คุณต้องเปิดไฟล์เอง) ยังไม่ใช่การถามแบบ interactive ระหว่างรัน

**เป้าหมายที่ยังไม่ทำ (backlog):** เมื่อ "ไพน้อย" เป็น production service จริง (ไม่ใช่ script รันมือ) ขั้นตอน Drawing Readiness Assessment ควร **หยุดรอ** ถ้าเจอคำที่ยังไม่เคย confirm มาก่อนเกินเกณฑ์ที่ตั้งไว้ แล้วส่งคำถามที่มนุษย์ตอบง่าย (เช่น "เจอบล็อกชื่อ X ยังไม่รู้จัก — เป็นวัสดุจริงหรือของตกแต่ง?") แทนที่จะเดินหน้าคำนวณ BOQ ต่อโดยไม่มีใครรู้ว่ามีอะไรถูกจัดหมวดผิดไปบ้าง — นี่คือสิ่งที่ Drawing Readiness Report (03-ai-boq-procedure.md Step 1.5) ควรทำเมื่อ implement เต็มรูปแบบ

## 7. ⚠️ ข้อควรระวังที่พบระหว่างพัฒนา — ห้ามใช้ `re.sub(pattern, string, text)` เขียนกลับ JSON

`apply_vocabulary_review.py` เคยทำ [04-category-schema.md](./04-category-schema.md) พังมาแล้วจริงระหว่างทดสอบ — ใช้ `re.sub(r"...", new_json_string, text)` แล้ว Python ตีความ backslash ใน **replacement string** เป็น backreference syntax (`\1`, `\g<...>`) ทำให้ backslash ของ regex pattern ที่เก็บไว้ใน `exclusion_rules.patterns` (เช่น `\\.`, `\\$`) หายไปครึ่งหนึ่งโดยเงียบๆ กลายเป็น JSON ที่ parse ไม่ผ่าน แก้แล้วโดยเปลี่ยนไปต่อ string ด้วย slicing (`text[:start] + new_content + text[end:]`) แทน — **บทเรียน:** เวลาเขียนสคริปต์ที่แก้ไฟล์ที่มีเนื้อหาเก็บ backslash (regex, path ฯลฯ) แบบอัตโนมัติ ต้อง test round-trip (โหลด-เขียน-โหลดใหม่) เสมอ ไม่ใช่แค่ดูว่ารันไม่ error
